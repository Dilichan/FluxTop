# v52: время приложений на логических процессорах

Зависимость — v51. PDH-данные `cpu_logical_usage` по-прежнему показывают общую
нагрузку логических процессоров. Новые `cpu_execution` показывают отдельную
ETW-атрибуцию времени процессов и групп приложений. Они не заменяют общий CPU
и не участвуют в AutoScore.

## Общая kernel-сессия

Владельцем остаётся DiskIoCollector. К прежним флагам Disk/File/Thread добавлены
PROCESS и CSWITCH. Отдельная CPU-сессия не создаётся. CpuEtwCollector открывает
второго потребителя существующей сессии с RAW_TIMESTAMP: время выполнения
рассчитывается в QPC. Прежний дисковый потребитель сохраняет стандартное
FILETIME-преобразование и свой алгоритм IRP/потоковой атрибуции.

Оба компонента требуют повышенный административный токен. Упрощённого
неадминистративного CPU/ETW-backend нет. При закрытии владелец останавливает
свою kernel-сессию и присоединяет оба потока ProcessTrace. CPU-потребитель
самостоятельно не останавливает общую сессию.

Старые сессии с префиксом FluxTop.Disk и отсутствующим/завершившимся владельцем
либо другим временем создания PID очищаются перед новым запуском. Живые
владельцы и чужие сессии не останавливаются.

## Топология и буферы

EVENT_HEADER_FLAG_PROCESSOR_INDEX выбирает systemwide ProcessorIndex.
Топология читается через GetLogicalProcessorInformationEx(RelationGroup),
с учётом активных масок и Processor Groups. Индекс не делится безусловно на 64:
группы могут быть заполнены частично. Старый ProcessorNumber разрешён только
при одной группе; при неоднозначности данные признаются недостоверными.
Изменение числа групп/процессоров требует перезапуска трассы.

Для достоверного CPU-контекста общая сессия использует буферы по процессорам.
Размер буфера — 16 КиБ, минимум max(256, 2 × число логических процессоров), максимум
2048 буферов (v54: резерв для всплесков CSwitch). CPU/ETW ограничен 512 логическими процессорами:
запрошенный максимум пула не превышает 32 МиБ. На большей топологии прежний
дисковый сбор остаётся доступным, CPU-атрибуция не включается.

В v54 владелец обнаруживает отказ/остановку трассы и потерю событий, оставляет
испорченные окна недостоверными и заменяет общую сессию после задержки 3–60 с.
Прежние потребители останавливаются до запуска новых; новая трасса начинает
с собственной базы. Изменение корреляции QPC/UTC также требует новой базы.
Реальное восстановление и очистку после аварии проверяет `etw_recovery`.
Подробная матрица и команды — [испытания стабильности](STABILITY.md).

## Идентичность и временные интервалы

- CSwitch V2–V5 декодируется по проверенному префиксу NewThreadId/OldThreadId;
  укороченное или неизвестное событие не угадывается. Для других доступных
  схем сначала используется TDH; отсутствие схемы — явная ошибка качества.
- Таблица потоков получает Start/DCStart/End/DCEnd, таблица процессов — события
  жизни процессов. Начальные живые потоки проверяются через Toolhelp и handles.
  Начальное перечисление выполняет потребитель после первого реального события:
  один OpenTrace ещё не гарантирует подключение ProcessTrace. Это закрывает гонку
  с созданием потоков во время запуска. Пока время доставленных событий не достигло
  времени регистрации, начальный неизвестный участок не атрибутируется.
- Владелец времени — PID вместе с creation time. Отложенный lifecycle event
  не связывается с новым процессом, повторно использовавшим PID. UTC/QPC-сверка
  нужна только для проверки идентичности; runtime считается исключительно по QPC.
  При изменении корреляции часов новые неподтверждённые владельцы остаются неизвестными.
- На каждом CPU хранится выполняющийся TID и захваченная при switch-in
  идентичность владельца. Миграция закрывает интервал на старом CPU и открывает
  новый. TID не может одновременно занимать два CPU.
- Первый неизвестный хвост, неизвестный владелец, отрицательное время и разрыв
  OldThreadId/NewThreadId не приписываются произвольному процессу.
- Граница окна фиксируется на обработанном ETW-времени в BufferCallback,
  а не на времени запроса клиента. Активные хвосты обрезаются на этой границе;
  следующий замер начинает их там же. Самплер забирает готовое окно и запрашивает
  следующее, не выполняя обработку событий на UI-потоке.
- Runtime — время запланированного выполнения между CSwitch; в него могут
  попадать прерывания/DPC внутри этого интервала. Это другой источник, чем
  GetProcessTimes, поэтому суммарный CPU по прежнему алгоритму не изменяется.

## Достоверность

`ready` означает полное покрытие окна всех логических CPU. `partial` —
неизвестные интервалы или процессоры. Для каждого CPU `percent` присутствует
только при полном покрытии именно его интервала. `observed_percent` и
`observed_runtime_ns` при partial — подтверждённая нижняя граница, не оценка
неизвестной части. Если владелец/трасса недостоверны, значения — null.

Потеря ETW-событий проверяется в BufferCallback и запросом состояния сессии
(EventsLost, RealTimeBuffersLost, LogBuffersLost). Потеря, разрыв переключений,
перестановка времени, перекрытие TID или превышение лимита состояния запрещают
выдавать окно за точное; восстановление — новая трасса/перезапуск. Простого
появления нескольких последующих событий недостаточно для восстановления ready.

`baseline` — начальное окно; `awaiting-window` — ещё нет следующего готового
окна; `stale` — окно старше 5 секунд или слишком длительное. Экспорт содержит
границы QPC, частоту и delivery_lag_ms. Все проценты относятся к указанному
ETW-интервалу, который может отставать от текущего UI на время доставки.

Таблицы ограничены 65 536 живыми потоками, 8 192 процессами/счётчиками и
131 072 ячейками process × CPU. Завершённые потоки удаляются сразу, завершённые
процессные счётчики — после закрытия окна. На горячем CSwitch-пути нет TDH
для известных схем; вектора счётчиков повторно используются между окнами.
Для отображения выполняющихся TID заранее выделен один узел хеш-таблицы на CPU:
переключение/простой переиспользуют его без выделения узла на каждый CSwitch.

## Модель и экспорт

Snapshot.cpu_execution_status и QPC-метаданные описывают общее качество.
Process.cpu_execution.logical содержит group, number, runtime_ns, percent и
observed_percent. JSONL экспортирует это как process.cpu_execution, а метаданные
окна — как верхнеуровневый cpu_execution. QPC-границы записываются строками
для сохранения 64-битной точности. Неизвестные значения не превращаются в нули.

aggregate_application_processes использует существующую группировку по полному
EXE-пути. Runtime и доли одного CPU суммируются между процессами только для
одного окна. Одинаковые имена в разных EXE-путях остаются разными приложениями.
Неподтверждённый участник группы оставляет известные значения нижней границей
и не позволяет назвать всю группу полностью измеренной.

## Проверки

- cpu_execution: форматы событий, QPC/наносекунды/проценты, границы окон,
  миграция, группы, PID/TID reuse, неизвестные интервалы, loss/overflow,
  ограничения состояния, группировка, JSON и неизменность AutoScore.
- cpu_etw_live (администратор): закреплённые и мигрирующие потоки, второй цикл
  с частыми переключениями, uncached physical writes, ровно одна новая kernel-
  сессия, обычное закрытие и аварийное завершение дочернего процесса с новым запуском.
  Масштаб суммарного ETW-времени сверяется с независимым GetProcessTimes, с допуском
  на начальный интервал и задержку доставки. Фиксированная минимальная загрузка
  не предполагается: конкурирующие задачи могут отнимать CPU у тестовых потоков.
- Прежние disk_attribution/disk_pipeline, история, JSONL и остальные регрессии
  входят в полный CTest Release. Без администратора live-тест явно skipped.

Реальная многогрупповая машина нужна для дополнительной аппаратной проверки
границы Group 0/Group 1; расчётные сценарии с несколькими группами входят в unit-тест.

### Результат проверки 23.11.2026

Release x64 собран MSVC с /W4 /WX. Полный CTest от администратора: 51/51,
без пропущенных тестов, 37,12 с; cpu_etw_live — 24,45 с. Машина: Windows
10.0.26200.0, 32 логических процессора, одна Processor Group.

В двух нагрузочных циклах суммарное наблюдённое время составило 8,845/11,124 с
при 14,250/18,141 с по GetProcessTimes за весь тестовый период. Разница включает
начальное неполное окно и ещё не доставленный конец трассы. Пройдены физические
записи одновременно с CSwitch, миграция между CPU, частые переключения, обычная
остановка и принудительное завершение собственного дочернего процесса с очисткой
сессии и новым рабочим окном. При исследованном переполнении ETW сборщик выдавал
incomplete; после увеличения ограниченного пула итоговый нагрузочный цикл прошёл.

Аварийный тест также выявил прежнюю ошибку очистки дисковых сессий: в ControlTrace
передавалась копия заголовка с размером полного буфера. Теперь используется исходный
буфер с хранилищем имени; проверка очистки после аварии проходит без повреждения стека.
