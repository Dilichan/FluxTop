# Методика проверки ресурсов

## Что измеряем

Рабочий режим: клиент свёрнут в трей, его окно уничтожено и ресурсы аналитики
освобождены, оверлей активен. Только для этого режима задаётся цель
≤50 МиБ (52 428 800 байт) Working Set и средний CPU ≤0,5% всей системы.
Учитываются сборщики, кеши и фоновая запись истории.
Private Bytes (commit), Peak Working Set и handles измеряются отдельно;
Private Bytes не приравнивается к физической RAM.
GPU в ожидании оценивается внешним инструментом.

Открытый клиент, построение графиков и запросы месячной/годовой/полной истории
не ограничиваются 50 МиБ. Для них отдельно фиксируются средняя/пиковая память,
CPU, время открытия, p95 запросов и отзывчивость. После возврата в трей
проверяется освобождение UI/результатов и возврат к рабочему бюджету после
периода стабилизации 30 секунд. Это не разрешение на неограниченный рост RAM.

Размер базы SQLite на диске не входит в бюджет 50 МиБ RAM. Для суммы
`fluxtop.db`, WAL и SHM действует аварийный лимит 50 ГиБ. История
сворачивается по минутам, часам и дням; см. [HISTORY.md](HISTORY.md).

Собственные метрики CLI не охватывают системные затраты PDH/ETW,
консольный хост и будущие вспомогательные процессы. Для итогового бюджета
нужен внешний замер всей конфигурации. Нельзя сравнивать peak с average
или выдавать короткий запуск на одной машине за подтверждение требований.

## Сценарии

Для каждого сценария записать commit, Release x64, версию Windows, CPU,
число логических процессоров, RAM, GPU/драйвер, число процессов, настройки,
интервал и длительность. Прогрев минимум 30 секунд, измерение минимум 10 минут.

1. CPU/RAM, GPU выключен, интервал 1 секунда.
2. CPU/RAM + GPU/dedicated memory, тот же интервал.
3. Отдельно: оверлей активен, клиент в трее — основной бюджет 50 МиБ.
4. Много процессов, запуск и завершение приложений, недоступные процессы.
5. Оконная и borderless-игра, несколько мониторов и разные DPI.
6. Открытый клиент: настройки, графики месяца/года/всего времени; отдельные метрики.
7. Возврат клиента в трей после тяжёлого запроса: освобождение памяти и рабочий бюджет.
8. Будущие ETW и запись истории: каждый источник отдельно, затем совместно.
9. Непрерывная работа 8 часов: рост Working Set, Private Bytes и handles.

Считать средний CPU по разности process CPU time за весь период и времени
периода с нормализацией на логические процессоры. Также показать p95/max
времени сбора, медиану/p95/max памяти и число пропусков интервала.
Замер с записью JSONL включает стоимость экспорта; фиксировать это в отчёте.

## Протокол результата

Для воспроизводимого замера собственных ресурсов прототипа:
скрипт ниже измеряет только CLI и не является приёмкой режима 50 МиБ с оверлеем.
Оверлей и клиент проверяются внешним замером в явно указанном режиме.

```powershell
.\tools\Measure-FluxTop.ps1 -Samples 600 -WarmupSamples 30
.\tools\Measure-FluxTop.ps1 -Samples 600 -WarmupSamples 30 -NoGpu
# Если сборка выполнена через Ninja:
.\tools\Measure-FluxTop.ps1 -Executable .\build\ninja\fluxtop.exe
```

Скрипт сохраняет в памяти только собственные метрики, а в отчёт не включает
имена процессов. CPU — среднее с весом по длительности интервалов; значения
CLI округлены до 0,001 процентного пункта. Это приближённый self-report,
для точной приёмки используйте независимую разность CPU time за весь период.
Прогрев скрипта добавляется к внутреннему начальному baseline сборщика.
Сценарий со стандартными параметрами занимает примерно 10,5 минуты.
Отчёт можно сохранить в `build/`, который исключён из Git.

```text
Commit / сборка:
Windows / оборудование / драйвер:
Сценарий / интервал / время / число процессов:
Режим: клиент в трее + оверлей / открытый клиент / аналитика / CLI:
Размер базы на диске / глубина истории / выбранный период:
CPU average:
Working Set median / p95 / max:
Private Bytes median / p95 / max:
Collection time p95 / max:
Handles start / end:
Внешний GPU idle:
Ограничения и неизвестные значения:
```

Текущий статус: измерений полной конфигурации с оверлеем и историей нет.
