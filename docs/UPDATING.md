# Обновление по согласию пользователя

## Скачиваемый FluxTop.exe

При открытии клиента монитор запускает установленный launcher с `--check-update`.
Только этот режим проверяет GitHub Releases Dilichan/FluxTop через WinHTTP.
Обычный запуск и автозагрузка Windows не проверяют релизы. Если найдена новая
версия, появляется вопрос на подтверждение; отказ не скачивает и не заменяет EXE.
Git и сборщик не требуются. Подходящие теги:
vX.Y.Z и vX.Y.Z-preview.N, включая Preview. Из последних 20 релизов выбирается
наибольшая версия выше текущей, с готовым asset FluxTop.exe и SHA-256 digest.
Draft, неподдерживаемые теги и неполные релизы пропускаются.

EXE скачивается по HTTPS, проверяются размер, SHA-256 из GitHub API, PE-заголовок
и встроенный release tag. Сначала сохраняется предыдущий launcher, затем новый
активируется в `%LOCALAPPDATA%\FluxTop\FluxTop.exe` и запускается отдельным
процессом. Ошибка активации восстанавливает предыдущий файл. Ошибка сети/TLS/
хеша не мешает запуску встроенного монитора; причина записывается в update.log.
TLS-проверки не отключаются. Сохранённый более новый launcher имеет приоритет
над старой копией EXE в Downloads, поэтому она не понижает версию.

Монитор извлекается в versions/<SHA-256>/; история и настройки общие между
версиями и не удаляются. После согласия загрузка и предварительная проверка
выполняются при работающем мониторе. Затем он получает WM_CLOSE, сохраняет
настройки и завершает сбор. Updater ждёт выхода процесса и только после этого
активирует новую версию и запускает её. Ошибку раннего завершения нового
процесса пока не обнаруживает ready-протокол (ADR-0001).
Постоянного фонового обновляющего процесса нет.

Тесты release_update/portable проверяют версии, JSON, хеш, активацию/rollback,
заблокированный файл, извлечение EXE и сохранность истории. Подробности
публикации: [PUBLISHING.md](PUBLISHING.md).

## Исходники и обновление через Git

Обычная точка запуска — `fluxtop.cmd` в корне checkout. Launcher проверяет
настроенную upstream-ветку, обновляет исходники, собирает Release и запускает
проверенный EXE. Прямой запуск `fluxtop.exe` оставлен для офлайн-работы и замеров:
сам сборщик не запускает Git и не держит updater в фоне.

Обновление — отдельный процесс, который запускается первым. Ошибка, мешающая
основному приложению стартовать, не должна блокировать получение фикса при
следующем запуске. Это закреплено в [ADR-0001](decisions/0001-independent-updater.md),
включая целевой протокол подтверждения старта и восстановления.

## Настройка

Нужны Git for Windows, Windows PowerShell 5.1+, MSVC x64, Windows SDK и CMake.
Ninja используется при наличии; иначе — Visual Studio generator.
Launcher находит инструменты в PATH или установленном Visual Studio Build Tools.

После клонирования обычная ветка уже имеет upstream. Для существующей копии
подключите репозиторий и upstream вручную. Адрес официального репозитория —
`https://github.com/Dilichan/FluxTop.git`; launcher читает адрес из Git config,
поэтому для форка можно использовать собственный remote.

```powershell
git remote add origin https://github.com/Dilichan/FluxTop.git
git fetch origin
git branch --set-upstream-to=origin/main main
.\fluxtop.cmd --samples 5
```

При обычном клонировании `git clone https://github.com/Dilichan/FluxTop.git`
remote и upstream создаются автоматически. Пустой репозиторий без HEAD/upstream
пропускает сетевое обновление. Команды выше предполагают существующую ветку `main`
с общей историей с remote; для новой рабочей копии используйте клонирование.

## Поведение

1. В один момент обновляет/собирает только один launcher данной копии.
2. Изменённые и неотслеживаемые файлы, detached HEAD, отсутствие upstream,
   незавершённый merge/rebase и локальные коммиты блокируют автоматическое слияние.
3. Выполняются fetch текущей upstream-ветки и только fast-forward к её commit.
   Нет reset, clean, stash, rebase, принудительного checkout и перезаписи правок.
4. Непроверенный сетевой результат не сливается при сбое fetch. Сеть имеет timeout,
   интерактивный запрос учётных данных отключён. Офлайн-запуск остаётся возможным.
5. Новая сборка проходит CTest и копируется в отдельный каталог `out/launcher/versions/`.
   Только затем атомарно переключается указатель `last-good.json`.
6. Неизменившийся чистый commit с уже подготовленным EXE повторно не собирается.
   Локальные правки при необходимости собираются отдельно и не стираются.
7. При ошибке сборки/тестов запускается предыдущий проверенный EXE, если он есть.
   При первом запуске без рабочего EXE ошибка завершается ненулевым кодом.

Исходники при неудачной сборке уже могут быть fast-forward обновлены;
откат рабочего дерева автоматически не выполняется. Старый EXE остаётся доступен.
Для исходной локальной копии fallback также ищется в `build/Release` и `build/ninja`.
Эти вручную собранные EXE не считаются проверенными launcher-ом.

## Управление

```powershell
# Обновить, собрать при необходимости, запустить с параметрами сборщика
.\fluxtop.cmd -StandardUser --no-gpu --samples 5 --jsonl

# Пропустить сетевую проверку
.\fluxtop.cmd -NoUpdate --samples 5

# Подготовить версию без запуска монитора
.\fluxtop.cmd -PrepareOnly
```

Launcher по умолчанию запускает готовый монитор через UAC в отдельном окне.
`-StandardUser` отключает запрос повышения: приложение наследует права и консоль,
его stdout сохраняет формат JSONL. Сообщения launcher-а идут в stderr.
После запуска EXE PowerShell завершается. Код выхода `fluxtop.cmd`
сообщает об успешном старте, а не о дальнейшем
завершении монитора. Для ожидания результата и точного exit code используйте
прямой запуск EXE, например в тестах и скриптах автоматизации.
В текущем прототипе «успешный старт» здесь означает только создание процесса.
Обнаружение его раннего падения и сигнал `ready` пока не реализованы;
`last-good.json` подтверждает сборку/тесты. Даже если EXE затем не запустился
нормально, следующий запуск launcher-а снова проверяет Git перед запуском EXE.
Логи сборки и состояния находятся только в исключённом из Git `out/launcher/`.
Старые версии автоматически не удаляются. После обновления самого launcher-а
его новый код применяется со следующего запуска.

## Доверие и ограничения

Для будущего запуска при входе в Windows предусмотрены задержка, скрытый
режим launcher-а и отдельная настройка проверки обновлений. Требования описаны
в [документе автозагрузки](AUTOSTART.md); режим -Autostart уже запускает
обновление скрыто после задержки, затем запрашивает UAC и открывает оверлей в трее.

Это обновление исходников из настроенной ветки, а не загрузка подписанного релиза
или сравнение SemVer-тегов. Настраивайте upstream на доверенную стабильную ветку:
новые CMake-файлы, тесты и EXE выполняются с правами текущего пользователя.
Git и сборка не требуют повышения. UAC для монитора вызывается только после
подготовки версии; отказ пользователя завершает запуск с кодом 1223.
Запускайте launcher из обычной консоли. Сборка и Git работают только перед стартом;
в бюджет фонового монитора они не входят. Автообновление отключается `-NoUpdate`.

Механика основана на [git fetch](https://git-scm.com/docs/git-fetch)
и [git merge --ff-only](https://git-scm.com/docs/git-merge).

## Проверки разработчика

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\update_tests.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\launcher_tests.ps1
```

Первый скрипт использует локальные bare/working репозитории в `build/`:
fast-forward, повторная проверка, локальные tracked/untracked правки, detached
HEAD, незавершённый merge, локальные коммиты, divergence и недоступный remote.
Также проверяются timeout дочернего процесса, quoting argv и путь last-good.
Второй требует уже собранного сборщика и проверяет fallback при ошибке CMake,
сохранность предыдущего EXE/manifest, блокировку и повторное использование
готового commit без пересборки. Проверки добавлены в Windows CI.
Тесты не обращаются к сетевому Git-сервису и не меняют рабочее дерево проекта.
