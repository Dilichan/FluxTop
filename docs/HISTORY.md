# История без автоматического удаления

История должна оставаться доступной за месяц, год и всё время работы FluxTop.
У базы на диске нет прикладного лимита размера, числа приложений, строк или
возраста записей. Ограничения свободного места и самого SQLite остаются
физическими ограничениями хранения, а не политикой удаления истории.

## Разделение данных

- `icons.db` уже реализована: уменьшенные PNG-иконки и EXE-пути. Ограничения
  2 МиБ / 256 записей и автоматическая чистка сняты. Обновление иконки того же
  EXE заменяет текущую картинку; это не удаление временного ряда метрик.
- `history.db` реализована: каждый замер записывает все процессы, их показатели
  и системные итоги. Экран аналитики и история событий ещё не реализованы.
- Ограниченный кеш SQLite, очередь записи и кеш декодированных иконок в RAM
  сохраняются: они определяют расход памяти, а не объём сохранённых данных.

## Требования к записи и аналитике

1. Сохранять измерения и события без TTL, retention и удаления старых периодов
   по расписанию, размеру файла или числу записей. Очистка — только явное
   действие пользователя с выбранным диапазоном и понятным подтверждением.
2. Хранить время в UTC, длительность измеряемого интервала, устойчивую
   идентичность приложения и экземпляра процесса, значения и признаки пропусков.
   Отсутствующие показатели не подменять нулём.
3. Поддерживать диапазоны «месяц», «год», «всё время» и произвольный период,
   включая уже закрытые и удалённые приложения. Не требовать живого PID для
   просмотра старой статистики и сохранённой иконки.
4. Индексы по приложению/времени и дополнительные дневные/часовые агрегаты
   ускоряют чтение. Агрегаты не заменяют исходные данные с их удалением.
   При расчёте средних учитывать длительность валидных измерений и пропуски.
5. Историю держать на диске. Один снимок записывается транзакцией в потоке
   сбора, без очереди из накопленных снимков. UI не выполняет SQL.
   Графики и таблицы должны читать выбранные периоды/порции/агрегаты, а не
   загружать всю базу при старте или в режиме трея.
6. При появлении записи истории её жизненный цикл не зависит от открытия
   клиента или видимости оверлея. Скрытие UI не должно останавливать включённую
   пользователем запись. Сбор и запись продолжаются и при скрытых обоих окнах.
7. При нехватке места или ошибке записи сообщать о проблеме, отмечать пропуск
   и сохранять уже записанные периоды. Не удалять старое молча ради новых данных.
8. Предусмотреть миграции, восстановление после аварии, экспорт и резервное
   копирование; перезапуск не должен обнулять накопленную историю.

## Режимы и память

**Рабочий режим:** клиент свёрнут в трей, его окно и ресурсы аналитики
освобождены, оверлей активен. Цель ≤50 МиБ RAM относится к этому режиму,
включая сборщики, необходимые кеши и фоновую запись истории.

**Открытый клиент:** настройки, графики и работа со статистикой имеют отдельные
метрики памяти, CPU, времени запросов и отзывчивости. Лимит 50 МиБ здесь
не применяется. Оптимизация обязательна: ленивое создание страниц, порционное
чтение и освобождение результатов после закрытия клиента.

После сворачивания клиента в трей приложение должно возвращаться к рабочему
бюджету, а размер накопленной базы не должен определять объём постоянно занятой RAM.
Методика замеров описана в [PERFORMANCE.md](PERFORMANCE.md).

## Реализованная схема (user_version = 1)

Путь по умолчанию: `%LOCALAPPDATA%\FluxTop\history.db`.
`FLUXTOP_HISTORY_DB` задаёт отдельный файл для тестов. База, WAL и SHM исключены
из Git. Данные и локальные EXE-пути не отправляются в сеть.

- `applications`: приложение по нормализованному полному EXE-пути; одинаковые
  имена в разных папках различаются. Недоступный путь отмечен ключом `name:`,
  его нельзя считать надёжной идентификацией приложения для будущей аналитики.
- `process_instances`: PID, время создания FILETIME, приложение и первое
  наблюдение. Повторное использование PID создаёт отдельный экземпляр.
  Без creation time идентичность ограничена текущим непрерывным наблюдением
  в рамках запуска; между перезапусками такие экземпляры не склеиваются.
- `snapshots`: UTC timestamp_ms, фактический interval_ms, системные CPU/RAM/GPU,
  GPU RAM, Rx/Tx и статусы сборщиков.
- `measurements`: одна строка на процесс и замер; CPU, working set, private
  bytes, GPU, local GPU memory, Rx/Tx. Недоступное — NULL, нулевое — 0.
- `history_state`: число успешно зафиксированных строк `measurements`.
  Оно обновляется в той же транзакции, что данные, и читается без полного
  COUNT(*) при запуске. Счётчик показан в клиенте под иконками в памяти.

TOP, видимые столбцы, прозрачность, режим только общих показателей и скрытие
оверлея не фильтруют историю. Интервал клиента 1–10 секунд задаёт и частоту
записи. Консольный диагностический --interval-ms сохраняет диапазон 250–60000.

Применяются индексы по времени и экземпляру процесса, WAL, synchronous=FULL,
кеш страниц 256 КиБ, mmap отключён. WAL checkpoint ограничивает журнал,
а не объём истории. В RAM кешируются только текущие экземпляры процессов.
Ошибка/блокировка откатывает весь замер и счётчик, показывается в клиенте;
следующий замер пробует записаться снова. Неудачный замер не буферизуется
бесконечно; пропуск виден по времени соседних сохранённых снимков. Старые
данные не удаляются. Неизвестная версия схемы не перезаписывается.

Тест history проверяет NULL/0, одинаковые имена в разных папках, PID reuse,
перезапуск, запись 1000 процессов без TOP, атомарный rollback, блокировку БД
и восстановление записи. Архив, экспорт и агрегаты для аналитики — следующий этап.
