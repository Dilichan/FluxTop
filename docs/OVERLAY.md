# Прозрачный оверлей и клиент

Оверлей содержит: уменьшенная иконка EXE, имя приложения,
CPU, RAM, GPU, память GPU, сетевые Rx/Tx. Текст белый с небольшой тенью для читаемости.
Заголовок «Приложение» начинается у левого края, над колонкой иконок.
Единственная строка шапки показывает общую нагрузку справа от названия
показателя: `CPU 12.3%`, `RAM 35.1%`, `GPU 4.0%`, `GPU RAM 3.1 GiB`.
Итоги не зависят от TOP:
CPU и RAM в процентах, GPU — загрузку самого занятого движка,
GPU RAM — общий объём dedicated memory адаптеров, Rx/Tx — скорости TCP/UDP.
Rx/Tx — один столбец: `1.2 / 3.4 MiB/s`, приём слева, передача справа.
Обе скорости используют общую единицу, выбранную по большей из них.
В режиме только общих показателей весь оверлей занимает одну строку.
Панель, логотип, название FluxTop, TOP-кнопки, PID и диагностический подвал
в оверлее отсутствуют. Название программы находится в заголовке клиента.

```powershell
.\fluxtop.cmd -NoUpdate --overlay
```

## Настройка в клиенте

- Размер текста 5–42 px и количество приложений 1–100 задаются ползунками;
  сортировка CPU/RAM/GPU/память GPU/Авто/Rx/Tx/Rx+Tx.
- Настройки применяются и сохраняются автоматически. При перетаскивании
  ползунка подпись обновляется сразу, а изменение параметра применяется
  с короткой задержкой или при отпускании. Кнопки «Применить» нет.
- Непрозрачность текста и иконок — ползунок 1–100%, фон всегда прозрачен.
- Отдельные флажки CPU/RAM/GPU/GPU RAM и единый Rx/Tx скрывают соответствующие столбцы.
  «Только общие показатели» убирает список и колонку названий. В начале сводной
  строки остаётся FPS активного окна. При отсутствии замера отображается `FPS: —`. Если снять все
  флажки метрик, остаются общие показатели всех ресурсов без списка приложений.
- Интервал сбора и обновления задаётся от 0,5 до 10 секунд с шагом 0,5 секунды.
  Он применяется без перезапуска сборщиков и сохраняется вместе с настройками.
  При коротких интервалах сортировка завершает движение строк до следующего замера.
- Включение иконок, режим показа, редактор сцены и чёрный список приложений.
- Статистика процесса FluxTop, состояние сборщиков и ошибки отображаются здесь.
- Закрытие клиента уничтожает окно настроек, оставляя оверлей и трей.
- Автозапуск при входе в Windows с запросом UAC: [UPDATING.md](UPDATING.md).

«Авто» рассчитывает рейтинг по текущей нормализованной нагрузке CPU, RAM,
GPU, VRAM и сети, дополняя его короткими всплесками. Каждый столбец
окрашивается независимо; скрытые показатели не влияют на рейтинг.
В первой строке отображается приложение активного foreground-окна Windows.
При этом остальные строки остаются в AutoScore-порядке. Смена окна обрабатывается
по событию, а сбор ресурсов идёт с пользовательским интервалом.
Режимы Rx и Tx сортируют по соответствующей скорости, Rx/Tx — по сумме.
Неизвестные значения не подменяются нулём.

Двойной клик по трею или Ctrl+Alt+F9 открывает клиент.
Ctrl+Alt+F10 приостанавливает или возобновляет показ оверлея.
Клики проходят сквозь оверлей. Чтобы изменить его положение, откройте
«Настроить сцену» и переместите прямоугольник на сетке нужного монитора.
Меню трея переключает страницы таблицы и графиков, если они не помещаются.

В автоматическом режиме один достоверный замер FPS добавляет приложение
в список показа по имени EXE. Пропуски следующих замеров не скрывают
оверлей. Чёрный список исключает выбранные приложения из автоматического показа
и показывает их названия и иконки. Режим «Показывать оверлей всегда» оставляет
оверлей на экране при смене фокуса и сворачивании клиента. Ручная пауза действует
в обоих режимах.

Настройки сохраняются в %LOCALAPPDATA%\FluxTop\overlay.ini.
Аргументы --top, --sort и --font-size имеют приоритет над сохранёнными значениями.
--font-size N принимает 5–42 и требует --overlay. Для изолированных проверок
FLUXTOP_OVERLAY_SETTINGS задаёт путь к отдельному INI.

## Многопроцессные приложения

Снимок Windows собирается по каждому PID. Только для оверлея процессы
объединяются в приложения по нормализованному **полному пути EXE**.
В отличие от одного дерева PID/PPID это включает отдельные корни Chrome,
Edge, Firefox, VS Code, Electron и других программ с одинаковым EXE-путём.
Если путь отсутствует, разрешено лишь проверенное родство PID/PPID с учётом
порядка создания процессов и совпадения имени при отсутствии обоих путей.
Совпадение **только имени** не объединяет независимые экземпляры.

Отдельные профили и окна одного EXE объединяются в одну строку. Разные пути
одного имени (например, установленные рядом стабильная и тестовая сборки)
остаются отдельными группами. При совпадении видимых имён оверлей добавляет
к названию краткое различие по каталогу установки (без полного EXE-пути и
без изменения ключа группировки). Подсчёт по путям не зависит от производителя CPU
или видеокарты.

CPU, Working Set, GPU RAM, Rx и Tx суммируются по отдельным PID без
дублирования PID. GPU% — **максимум** нагрузки среди процессов группы;
складывать проценты разных движков некорректно. Working Set может включать
разделяемые физические страницы, поэтому это не размер уникальных страниц в RAM.
В многопроцессных приложениях отображаются **только подтверждённые значения**
доступных PID: CPU, Working Set, GPU RAM, Rx и Tx суммируются, а GPU% — это
максимальная загрузка среди измеренных процессов. Недоступный процесс не
подменяется нулём, но не скрывает корректные значения остальных процессов.
Если **ни у одного** PID нет измерения конкретного ресурса, выводится «—»;
реально измеренный ноль остаётся нулём. Без знака «≥» для GPU RAM.
Такой же измеренный поднабор используется в раскраске оверлея, сортировке,
AutoScore, подсказках статистики и истории. Значение при частичном охвате не
является полной оценкой потребления всех процессов приложения. При
разделяемых GPU-ресурсах сумма выделений отдельных PID может превышать
текущую физическую занятость адаптера. Индивидуальные значения проверяются
до группировки, но подтверждённая сумма не отбрасывается повторной проверкой.
Физический дисковый I/O остаётся отдельной подтверждённой нижней границей (≥)
при неполной ETW-атрибуции, а не «полной суммой приложения».
Журнал `metrics.coverage` каждые 15 снимков (и на первом) сообщает число
доступных значений каждого ресурса; `gpu_status=ready` означает работающий
сборщик, но не полный доступ к памяти GPU всех процессов.
Исходники семантики Windows: GetProcessMemoryInfo (WorkingSetSize), GetProcessTimes,
D3DKMTQueryVideoMemoryInfo, Configuring and Starting a SystemTraceProvider Session
на learn.microsoft.com. Разница с Get-Process также зависит от момента измерения.

Авто-рейтинг и всплески рассчитываются по агрегированным приложениям. Окно
любого дочернего или независимого процесса группы закрепляет всю группу первой
строкой. SQLite/JSONL и исходный снимок сохраняют детальные записи по PID.

## Рендеринг и жизненный цикл

Сборщики работают в отдельном потоке; mailbox хранит только последний снимок.
Оверлей рисуется Direct2D/DirectWrite в ARGB-поверхности и выводится через
UpdateLayeredWindow. У фона нулевая альфа; буквы и иконки имеют собственную альфу.
Полупрозрачной прямоугольной панели нет. Перерисовка событийная, без 60 FPS.

При скрытии оверлея графические ресурсы освобождаются. Сборщики и запись
истории продолжаются даже при закрытом клиенте. Между началом соседних сборов
выдерживается выбранный интервал; при слишком долгом сборе нет цикла догоняющих
замеров. UI получает последний снимок без очереди старых обновлений.
Запись всех процессов и счётчик строк описаны в [HISTORY.md](HISTORY.md).

## Иконки приложений

Иконка извлекается из EXE в фоновом потоке, уменьшается до 32×32, кодируется
в PNG и хранится BLOB-ом в %LOCALAPPDATA%\FluxTop\icons.db.
Используется системная SQLite Windows (winsqlite3.dll), без отдельного сервера.

- Размер БД и число сохранённых путей не ограничены приложением; автоматической
  чистки по количеству записей нет. Кеш страниц SQLite в RAM — 128 КиБ.
- Ключ: EXE-путь, время изменения и размер файла. Изменение EXE обновляет запись
  при следующей загрузке иконки из дискового кеша.
- В памяти максимум 64 декодированных изображения — около 256 КиБ пикселей.
- Очередь ограничена; отрицательные результаты тоже кешируются.
- При недоступной БД используется память; при недоступном EXE — системная иконка.
- БД содержит локальные EXE-пути, не отправляется по сети и исключена из Git.

Для тестов FLUXTOP_ICON_DB задаёт путь БД внутри build/.
При измерении бюджета учитываются WIC, SQLite, шрифты и все потоки процесса.
Лимит 50 МиБ относится к активном оверлее при свёрнутом в трей клиенте.
Открытый клиент измеряется отдельно. Сворачивание и закрытие окна клиента
освобождают его ресурсы, сохраняя оверлей и трей. История и кеши разделены:
см. [HISTORY.md](HISTORY.md).

## Границы

Консольный режим и JSONL сохраняются. --overlay несовместим с --jsonl;
--samples N завершает диагностический UI-запуск после N снимков.
Сцены, экран аналитики и протокол ready updater-а ещё не завершены.
Оверлей работает в оконном/borderless режиме без внедрения кода в игры.

## Показатели и сеть

CPU всей системы: GetSystemTimes; RAM: GlobalMemoryStatusEx.
GPU всей системы: сумма процессов по каждому PDH GPU Engine и максимум
между движками (0–100%), без сложения процентов независимых движков.
Общая GPU RAM берётся из GPU Adapter Memory, без суммирования строк процессов.
Память отдельного процесса: D3DKMTQueryVideoMemoryInfo, CurrentUsage локального
сегмента по адаптерам/физическим узлам. На UMA локальный сегмент может быть
системной памятью. JSON-имя dedicated_gpu_bytes сохранено для совместимости.
Недоступный запрос показывает «—», не прошлое значение или фиктивный ноль.
Известный проблемный счётчик PDH GPU Process Memory больше не используется как
подмена нулей или недоступных D3DKMT-запросов (Microsoft KB 4490156).
Для измерения видеопамяти процесса D3DKMT открывает дескриптор с
PROCESS_QUERY_INFORMATION. На проверенной системе ограниченный дескриптор
PROCESS_QUERY_LIMITED_INFORMATION возвращал STATUS_ACCESS_DENIED при каждом
запросе D3DKMT и приводил к лишней попытке для каждого процесса. Права
администратора при этом не требуются для доступных пользовательских процессов;
защищённые процессы могут оставаться недоступными. Данные проверяются по
времени создания PID; неизвестные значения не заменяются PDH и не участвуют
в AutoScore. Обобщённая диагностика: gpu.memory.access.
Если D3DKMT-показание отдельного процесса больше известного общего использования
адаптеров или физической ёмкости локального сегмента, оно считается
несопоставимым и не передаётся в AutoScore. Числа не обрезаются до лимитов.

Rx — приём, Tx — передача; единицы B/s, KiB/s, MiB/s. Используется отдельная
системная ETW-сессия только с NETWORK_TCPIP: TCP/UDP, IPv4/IPv6. Учитываются
события Send/Recv; LAN и loopback входят в показатели. Это не счётчик оплаты
интернет-провайдера: VPN, прокси и локальные сервисы могут менять атрибуцию.
Пакеты и адреса не сохраняются; только суммы байтов по PID за интервал.
Есть задержка доставки ETW около секунды. PID сверяется с временем создания.
Системный итог включает и процессы, которых уже нет в текущем списке.
При недостаточных правах сеть имеет статус administrator-required, при потере
событий или ошибке разбора — incomplete; значения показываются неизвестными.
Восстановление после ошибки — перезапуск сборщика/программы.
--no-network отключает ETW. При завершении сборщика его ETW-сессия закрывается.
Память её буферов ограничена настройками 2–8 × 64 КиБ
без отдельных буферов на каждый CPU; реальную стоимость измеряем отдельно.
После аварии следующий сборщик очищает только сессии FluxTop с отсутствующим
владельцем или другим временем создания PID. Живые/недоступные владельцы
и чужие ETW-сессии не останавливаются.

Интеграционный тест build/ninja/fluxtop_network_tests.exe запускают с правами
администратора; он создаёт только loopback TCP/UDP IPv4/IPv6. Без повышения
CTest отмечает его пропущенным (код 77).

Источники: [GPU memory counter issue](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value),
[D3DKMTQueryVideoMemoryInfo](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtqueryvideomemoryinfo),
[system ETW sessions](https://learn.microsoft.com/en-us/windows/win32/etw/configuring-and-starting-a-systemtraceprovider-session).


## Автоматическая сортировка

AutoScore — эвристика для приоритизации внимания, а не оценка мощности ПК
или энергопотребления. Ресурсы нормализуются в сравнимые оценки; важны
доминирующий ресурс, второй по величине показатель и кратковременные всплески.
Сглаживание уменьшает случайные перестановки, но не должно скрывать значимые
скачки. Пара PID и время создания защищает от переиспользования PID.
Методические основания: [MCDA](https://pmc.ncbi.nlm.nih.gov/articles/PMC9433668/),
[Dominant Resource Fairness](https://www.usenix.org/conference/nsdi11/dominant-resource-fairness-fair-allocation-multiple-resource-types)
и [EWMA](https://doi.org/10.1080/00401706.1990.10484583).

Столбец «Диски» показывает подтверждённые ETW скорости чтения+записи по
всем физическим накопителям для конкретного приложения; `Disk C`, `Disk D` и
другие — подтверждённые операции конкретного тома. В заголовках `Disk X`
остаётся общесистемный процент активности логического тома PDH, тогда как в
строках — скорость MiB/s (или KiB/s). Неизвестные величины — «—».

ETW использует начало физической операции DiskIo ReadInit/WriteInit
и завершение DiskIo по одному IRP, направлению и времени. Если DiskIo Init
не удалось подтвердить, возможна консервативная корреляция с FileIo Read/Write
по IRP и FileObject. Для событий с системным PID дополнительно используется
IssuingThreadId: действующий владелец потока через OpenThread либо ограниченная
по жизненному циклу таблица ETW Thread Start/DCStart/End. PID не угадывается;
System/кеш-менеджер без подтверждённого инициатора остаётся неизвестным.
Диагностика сообщает init_events, init_usable, init_matches, owner_header,
owner_open_thread, owner_etw, owner_system, owner_unknown_tid, сведения об
ошибках OpenThread и числе отслеживаемых потоков. Нулевые совпадения
остаются неизвестной нагрузкой.
Физическое смещение соотносится с диапазонами
IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS. Неоднозначные разделы и записи кеша System
не распределяются искусственно по приложениям. Потеря событий ETW делает интервал
недостоверным (incomplete). При неполном сопоставлении интервал получает статус
partial-attribution: публикуются **только подтверждённые операции** как нижняя
граница (знак `≥` в оверлее), отсутствующие совпадения остаются неизвестными (`—`).
Никаких фиксированных 80%: покрытие приводится в журнале как измеренный процент,
но не служит порогом достоверности отдельных операций. Нулевое значение допустимо
только при полном сопоставлении наблюдавшегося физического обмена. AutoScore
учитывает лишь подтверждённые операции и известную активность тома, поэтому на
частично покрытых системах может недооценивать дисковую нагрузку. Каждые 15 секунд
`disk_io.coverage` записывает без имён файлов статистику совпадений IRP.
`GetProcessIoCounters()` остаётся только диагностикой.

AutoScore при включённом общем или отдельном дисковом столбце принимает седьмую
категорию: долю активности диска, распределённую по подтверждённым физическим
байтам (`disk_busy% × process_disk_bytes/physical_volume_bytes`). Это эвристика,
не измерение точного сервисного времени. Нет фиксированных MiB/s порогов для
NVMe/SATA/HDD. История SQLite продолжает содержать ранние оценки до появления
дисковой атрибуции; старые записи нельзя переинтерпретировать без сырого ETW.
Документация: https://learn.microsoft.com/en-us/windows/win32/etw/diskio-typegroup1,
https://learn.microsoft.com/en-us/windows/win32/etw/fileio-readwrite,
https://nvmexpress.org/specification/nvm-express-base-specification/ и
https://sata-io.org/system/files/specifications/SerialATA_Revision_3_5_Gold.pdf.

Режимы анимации не используют мигание или затухание строк: меняется только
вертикальная позиция. Для большого числа строк предыдущие позиции индексируются
по PID, а перерисовка ограничивается изменившимися областями. Медленные кадры
регистрируются в диагностическом журнале; частота кадров адаптируется к цене
рендеринга. Это не влияет на интервал получения ресурсных показателей.

Рейтинг «Авто» берёт максимум нормализованной текущей нагрузки и всплеска по каждому видимому показателю.
Высокая постоянная нагрузка остаётся в списке после прекращения роста.
Небольшое затухание прошлого приоритета действует только пока показатель остаётся значимым.
Процессы сопоставляются по PID и времени создания; при повторном использовании PID предыдущая история игнорируется.
Цвет каждого числового показателя CPU/RAM/GPU/GPU RAM определяется собственной фактической загрузкой независимо от сортировки. Всплески продолжают участвовать в AutoScore, но не вызывают мигания или оранжевого выделения строк.
Общие показатели в заголовке имеют собственные цветовые пороги.
## Цвета и температуры в заголовке (0.2.1)

CPU/RAM/GPU окрашиваются по общесистемному проценту: 0–<50 зелёный,
50–<70 жёлтый, 70–100 красный. GPU RAM окрашивается только когда известны
использованный объём и ёмкость dedicated VRAM; показывает только занятый объём в GiB.
Rx/Tx не окрашивается процентными порогами, так как это байты/с.
Температуры: <65°C зелёный, 65–80°C жёлтый, >80°C красный.
GPU температура — WDDM D3DKMT (либо поддерживаемый аппаратный монитор).
CPU температура — HWiNFO Shared Memory или WMI сенсоры LibreHardwareMonitor/
OpenHardwareMonitor; датчик платы/ACPI отмечается отдельно. Недоступное — прочерк.
HWiNFO не поставляется вместе с FluxTop. Значения разных GPU могут отличаться;
пока для шапки используется наибольшая валидная температура.

Всплески используются в авторейтинге, но не меняют цвет текста или яркость
строк. Скрытый показатель не влияет на рейтинг. Видеопамять по процессам
может включать общие/разделяемые ресурсы и не обязана суммироваться до
общесистемного использования GPU.
## Отдельные переключатели цветов (0.2.1)

В клиенте есть два независимых флажка:

- «Окрашивать общие показатели» включает/выключает цветовую индикацию загрузки
  системы и температуры CPU/GPU в первой строке. При выключении значения белые.
- «Окрашивать строки оверлея» включает/выключает цвета только в строках
  процессов; сортировка «Авто» от этого не меняется.

Каждый доступный показатель CPU/RAM/GPU/GPU RAM окрашивается независимо от сортировки:
0–<50% использования — зелёный, 50–<70% — жёлтый, от 70% — красный.
Для CPU/GPU используется исходный процент нагрузки; для RAM/GPU RAM — доля
ёмкости физической памяти или выделенной VRAM. Вес AutoScore на цвет не влияет.
Детекция всплесков используется для режима «Авто» без мигания или смены
цвета чисел. Для Rx/Tx нет знаменателя загрузки, поэтому их текст остаётся
белым независимо от текущей скорости и всплесков.
Неизвестные показатели не окрашиваются.

Флажки по умолчанию включены и сохраняются отдельно в overlay.ini
как header_colors и row_colors. Данные измерений и рейтинг не изменяются.
## Закрепление активного окна в «Авто»

В «Авто» первый слот занимает группа приложения, которой принадлежит активное
foreground-окно Windows. Поддерживаются окна любого дочернего или другого
процесса **той же EXE-группы**. Остальные приложения сохраняют порядок AutoScore.
Переключение окон происходит по EVENT_SYSTEM_FOREGROUND без постоянного опроса;
снимки данных продолжают поступать с обычным интервалом.
При отсутствии PID в снимке действует стандартный рейтинг. Правило не
действует в других режимах сортировки. Закреплённая строка остаётся видимой
при прокрутке и не дублируется.


## Настройка геометрии столбцов

Ширины и отступы таблицы задаются **только в** `include/fluxtop/overlay_layout.hpp`, в `overlay_layout`. 
Поле `metric_widths` содержит CPU, RAM, GPU, GPU RAM и Rx/Tx. Для динамических
столбцов используются `disk_width` и `cpu_core_width`. Там же задаются ширина
приложения, место для иконки, промежутки и отступы по краям.

`calculate_overlay_table()` возвращает координаты базовых и динамических ячеек
и общую ширину. Эту геометрию используют окно, заголовки, строки и отсечение при отрисовке.
Текст базовых столбцов проходит через `draw_base_row()` и при прямой отрисовке, и при заполнении растрового кеша для анимации.
Изменения C++ требуют пересборки Release; ранее установленный EXE не обновляется автоматически.

## Достоверность температуры CPU (v39)

Показание CPU берётся только из идентифицированного CPU Package/Die/Core или
явно помеченного резервного датчика платы/ACPI. VRM, PCH, зоны без имени CPU
и TjMax не считаются температурой процессора. При отсутствии валидного
источника отображается `—`; последний известный результат не сохраняется
бесконечно. Приоритет: датчик кристалла/пакета выше датчика платы, данные
HWiNFO проверяются на свежесть (30 секунд), WMI читается отдельно от потока
замеров и имеет ограничение времени перечисления. В `temperature.cpu`
журналируется только смена источника/состояния (в том числе причины
недоступности), а не каждый измеренный градус или каждое обновление.
