# Архитектура

## Границы компонентов

Обязательное решение: [ADR-0001 — независимый updater](decisions/0001-independent-updater.md).
Обновление и основной монитор — отдельные процессы. В checkout нативный
Git-launcher проверяет upstream до запуска монитора, поэтому ошибка монитора
не мешает получить исправление на следующем запуске. Установленный launcher
проверяет GitHub Releases при открытии клиента, а не при обычном запуске.
Скачиваемый FluxTop.exe использует
WinHTTP, проверяет SHA-256/размер/тег и извлекает встроенный монитор. В checkout
нативный `FluxTopSource.exe` отдельно выполняет Git fetch, CMake/CTest и запуск
монитора; исходный автозапуск выполняет `FluxTopSourceAutostart.exe`. Для
установленного EXE используется собственный launcher без Git и компилятора.
Деинсталлятор `Uninstall-FluxTop.exe` встроен в скачиваемый EXE и извлекается
при установке; он удаляет только программные компоненты, сохраняя данные.
Подробнее: [PUBLISHING.md](PUBLISHING.md).

```text
Windows API -> ProcessCollector ----+
PDH --------> GpuCollector ---------+-> Snapshot -> сортировка -> console / JSONL
ETW --------> NetworkCollector ----+           -> Overlay / client
                                   |           -> HistoryWriter (SQLite)
Foreground events -> SceneManager (планируется)
```

Консольный режим выполняет сбор и вывод в одном потоке. Режим оверлея
использует отдельный поток сбора и Win32 message loop на UI-потоке.
Один общий Sampler формирует метрики в обоих режимах; UI получает последний
снимок через ограниченный mailbox и PostMessage. Клиент настроек создаётся по
запросу и уничтожается при закрытии. При скрытых обоих окнах сбор и история
продолжаются. Иконки извлекаются и сжимаются отдельным потоком
с ограниченной очередью и SQLite-кешем. Постоянного busy loop и render loop нет.
Модель снимка отделена от Windows API; детали UI — в [описании оверлея](OVERLAY.md).

## Данные

Снимок содержит UTC-время, количество процессов, длительность сбора,
число недоступных процессов, собственные ресурсы и список метрик.
Строка процесса содержит PID, время создания, имя и optional-показатели.
CPU рассчитывается из разности kernel + user time и монотонного времени
между измерениями, делённой на число активных логических процессоров.
Baseline хранится только для процессов текущего снимка: завершённые
процессы удаляются, повторно использованный PID получает новый baseline.

GPU-экземпляры PDH связываются по PID. Связывание не атомарно со снимком
процессов, поэтому возможна погрешность при очень короткоживущих процессах
и повторном использовании PID. Слияние для нового baseline пропускается.
Неуспешный опрос не должен оставлять прошлые значения как актуальные.
GPU RAM процесса запрашивается через D3DKMTQueryVideoMemoryInfo с проверкой
creation time; память всей системы — GPU Adapter Memory, а не сумма процессов.
GetSystemTimes и GlobalMemoryStatusEx дают системные CPU/RAM.
NetworkCollector владеет отдельной ETW-сессией TCP/UDP, потребитель работает
в отдельном потоке, в RAM только агрегаты последнего интервала по PID.
Снимок содержит системные Rx/Tx и скорости каждого процесса. Сеть можно
отключить --no-network; подробности и границы в [OVERLAY.md](OVERLAY.md).

Сцены впоследствии идентифицируют приложение по нормализованному пути EXE,
с дополнительными правилами окна. PID в постоянных настройках не хранится.

## Жизненный цикл ресурсов

- HANDLE и PDH query закрываются через RAII, включая пути исключений.
- Первый CPU/GPU sample может быть неизвестен, пока нет двух измерений.
- GPU не инициализируется при отключении сборщика.
- Динамические PDH-буферы переиспользуются и имеют защитный предел размера.
- У UI нет перерисовки 60 FPS; обновление приходит после снимка или изменения настроек.
- При скрытии оверлея render target освобождается.
- При закрытии настроек уничтожается окно и принадлежащие ему ресурсы.
- История накапливается в ограниченных агрегатах и записывается фоновым
  потоком после завершения интервала; UI-поток не выполняет SQLite-запись.
- История агрегируется по завершённым минутам/часам/суткам, хранит суточные
  агрегаты до 3660 дней и останавливает запись при угрозе лимиту 50 ГиБ.
  Рабочие очереди и кеши в RAM ограничены; см. [HISTORY.md](HISTORY.md).
- Бюджет 50 МиБ применяется к активному оверлею с клиентом в трее.
  Открытый клиент/аналитика имеют отдельные показатели; после закрытия их
  ресурсы освобождаются. См. [политику истории](HISTORY.md).

## Ошибки и безопасность

Отказ доступа к отдельному процессу — нормальное частичное измерение.
Ошибка создания системного snapshot — ошибка всего цикла и ненулевой код выхода.
Отказ GPU backend не останавливает CPU/RAM; экспорт отражает недоступность.
Launcher запрашивает UAC для монитора после подготовки версии; Git и сборке
повышение не требуется. Для автоматизации есть `-StandardUser`.
Границы прав описаны в [ADR-0002](decisions/0002-administrator-monitor.md).
Сам сборщик не делает сетевых запросов. Загрузка драйверов и изменение параметров
наблюдаемых процессов не предусмотрены. Пользовательский автозапуск реализован
через ярлык Windows, задержку 30 секунд и стандартный запрос UAC. Для
установленного выпуска автозапуск использует его Win32 launcher, для checkout —
оконный нативный `FluxTopSourceAutostart.exe`. Исходный launcher перед стартом
проверяет Git upstream и выполняет сборку/CTest; загруженный EXE проверяет
GitHub Releases только при открытии клиента. Жизненный цикл описан в
[документации обновлений](UPDATING.md).
Целевой протокол включает подтверждение готовности монитора и ограниченный
fallback при провале старта. В текущем launcher-е пока проверены сборка и CTest;
подтверждение `ready` и восстановление после раннего падения ещё не реализованы.

Экспорт — UTF-8 JSON Lines, одна запись на снимок, `null` для неизвестного.
stdout содержит только данные выбранного формата, диагностика — stderr.
Строки имён экранируются. Полные пути и window titles не входят в начальный экспорт.
