# Архитектура

v53: [настройки ядер, динамические CPU-столбцы и ряды существующих графиков](CPU_UI.md).
UI использует топологию и измерения Snapshot, а отрисовка остаётся в draw_chart_core().

## Модульная архитектура

Границы CMake и температурный контур внедрены. Остальные сборщики расширяются
в этих же границах по мере появления новых источников и показателей.

FluxTop показывает, какие процессы потребляют ресурсы ПК. Состав оборудования
и доступных показателей определяется на машине пользователя. При закрытом
клиенте продолжается сбор всех доступных показателей для истории и AutoScore.
Видимость столбца, открытие статистики и пауза графика отвечают за отображение.

### Блоки и границы ответственности

```mermaid
flowchart LR
    Inventory[Инвентаризация ПК] --> Sampler[Координатор сбора]
    Sampler --> Providers[Провайдеры измерений]
    Providers --> Normalize[Выбор источника и проверка измерений]
    Inventory --> Normalize
    Normalize --> Snapshot[Snapshot]
    Snapshot --> Apps[Группировка и AutoScore]
    Snapshot --> History[SQLite и JSONL]
    Apps --> UI[Оверлей и статистика]
    History --> UI
```

| Блок | За что отвечает |
| --- | --- |
| Инвентаризация | Находит устройства и процессорную топологию через Windows. Выдаёт идентичность устройства и наблюдаемые возможности, например драйвер, поддержку API и доступ к нужным счётчикам. |
| Провайдер | Читает один источник данных, например PDH, ETW, PawnIO или WMI. Владеет дескрипторами, сессиями, временными буферами и своим состоянием. Возвращает исходное измерение с временем, источником и результатом опроса. |
| Подсистема метрики | Проверяет единицы, область, актуальность и качество. Выбирает источник для конкретного устройства и показателя. Здесь находятся правила совместимости и резервирования источников. |
| Координатор `Sampler` | Запускает применимые провайдеры, планирует опрос, собирает согласованный снимок. Ошибки отдельных провайдеров отражаются в их метриках. |
| Модель и потребители | `Snapshot` передаёт нормализованные данные. Группировка, AutoScore, SQLite, JSONL и интерфейс используют этот контракт. Форматирование, геометрия оверлея и шаблон графиков принадлежат интерфейсу. |

Для реализации достаточно текущего стека C++20, Win32 и CMake. Границы
закрепляются отдельными целями сборки и небольшими заголовками. Регистрация
провайдеров явная, через обычный C++ в контуре сбора. Достаточно одного цикла
периодического сбора. Существующие ETW и другие блокирующие API используют
рабочие потоки там, где этого требует их API. Установщик и updater сохраняют
отдельный жизненный цикл по [ADR-0001](decisions/0001-independent-updater.md).

В текущей сборке `fluxtop_core` содержит модель и чистые вычисления,
`fluxtop_collectors` владеет адаптерами Windows, а `fluxtop_history` отвечает
за запись истории. Оверлей получает снимки через `sampling_worker.hpp`.
`architecture_boundaries` проверяет транзитивные зависимости этих интерфейсов.

### Как поддерживать разные ПК

1. **Обнаружение перед запуском.** Для каждого устройства подсистема проверяет
   признаки, необходимые провайдеру. Производитель или модель уточняют выбор,
   когда источник специфичен для оборудования. Фактическая доступность
   определяется драйвером, правами и пробным вызовом. Например, штатный
   драйвер может отдавать GPU Engine, но не предоставлять температуру.
2. **Один выбранный источник на показатель и устройство.** Провайдеры CPU
   Package сравниваются по типу датчика, актуальности и приоритету источника.
   При отсутствии пригодной температуры выбирается совместимый резервный
   источник. Топология Windows остаётся общей для температур и нагрузки ядер.
   На AMD провайдер Intel DTS пропускается, а общая топология и другие
   применимые источники продолжают работать.
   На ПК с двумя GPU применимость определяется отдельно для каждого адаптера.
   Например, встроенная графика может показывать свою загрузку при неизвестной
   температуре. Температура дискретного GPU относится к его строке.
   В текущем температурном контуре `cpu_topology.cpp` получает общую топологию
   без обращения к драйверу датчиков. Intel DTS использует её для адресации
   ядер, а `temperature_selection.cpp` сравнивает кандидатов по типу и свежести.
   WMI запускается по необходимости, засыпает при пригодном приоритетном
   показании и возобновляет опрос при его потере. При старте Intel DTS резерв
   ждёт результат до двух секунд. Если запрос уже выполняется, он завершается,
   после чего новые запросы прекращаются до возобновления потребности.
3. **Состояние и восстановление.** Подсистема различает несовместимость,
   отсутствие доступа, ожидание базы для расчёта, частичное покрытие, потерю
   событий, устаревание и временный отказ. Для несовместимого источника работа
   ограничивается проверкой возможностей. Временный отказ повторяется с
   задержкой. Изменение конфигурации или восстановление устройства позволяет
   пересчитать применимость. При смене источника счётчики получают новую базу.
4. **Общий ресурс с одним владельцем.** Если несколько показателей используют
   одну сессию или опрос, они получают данные от существующего владельца.
   Дисковый I/O и атрибуция CPU уже используют одну kernel ETW-сессию.
   Подсистемы определяют необходимые события и разделяют потребление данных.
   `EtwSession` отвечает за создание, контроль потерь и завершение сессий
   сети, CPU/дисков и FPS. Форматы времени и обработчики событий остаются у
   потребителей. При восстановлении сессию можно удалить только после проверки
   полного формата имени, PID и времени создания прежнего владельца.
   FPS использует отдельную сессию без флага системного логгера, с
   фильтрацией DXGI/D3D9 по PID. Сборщик связывает начало и конец Present по
   потоку, считает интервалы по QPC и сбрасывает показание при смене фокуса
   или потере событий. История FPS хранится в общем 30-минутном кеше графиков.

### Контракт нового показателя

В описании метрики рядом с кодом фиксируется следующий минимум.

| Поле | Что зафиксировать |
| --- | --- |
| Смысл | Система, устройство, процесс или приложение. Пример: время исполнения процесса на физическом ядре за интервал. |
| Единицы и формула | Базовые единицы, знаменатель процента и смысл нуля. Сеть хранится как байты в секунду, интерфейс форматирует выбранную единицу. |
| Идентичность | Для процесса PID и время создания. Для логического CPU группа и номер процессора. Для GPU идентификатор адаптера, а для диска — соответствие тома физическому устройству. |
| Время и качество | Возраст показания или начало и конец интервала. Источник, доступность и полнота атрибуции. Достоверный ноль сохраняется числом. Неизвестное значение — `nullopt`, `null` в JSONL и прочерк в UI. |
| Агрегация | Когда значения можно складывать по процессам, когда нужно брать максимум и когда суммирование привело бы к двойному учёту. Для истории определяются правила минутного, часового и суточного ряда. |
| Потребители | Где показатель уже есть или появится. Для AutoScore определяются вес и способ избежать повторного учёта той же нагрузки. Старые записи SQLite и существующие поля JSONL должны оставаться читаемыми. |

Добавление источника к существующей метрике должно укладываться в её
подсистему и тесты. Например, новый способ получить CPU Package добавляет
кандидата в существующий выбор датчика. Для отдельной метрики сначала
фиксируется контракт, затем метрика подключается к тем потребителям, которым она нужна.

### Как архитектура помогает ловить ошибки

- **Границы сборки.** Модель и общие расчёты компилируются без заголовков
  провайдеров. UI опирается на модель и чтение истории. Проверка зависимостей
  в CI ловит прямое и косвенное включение аппаратных API в UI или модель.
- **Тестовый провайдер и управляемое время.** Проверку формул, выбора
  источника, устаревания и повторных попыток можно прогонять на обычном ПК.
  Фикстуры подают подтверждённый ноль, отсутствующее значение, неполный
  интервал и восстановление источника без подключения соответствующего устройства.
- **Матрица интеграции.** Проверки покрывают несколько адаптеров, отсутствие
  драйвера или доступа, PID/TID reuse, потерю событий и смену конфигурации.
  Для затронутых потребителей тестируется путь от снимка до JSONL, истории и UI.
  Реальные проверки на Intel, AMD и разных GPU дополняют общие тесты.
- **Проверка жизненного цикла.** Обязательные сценарии для нового владельца
  ресурса — успешный старт, отказ при запуске, остановка и повторный старт.
  Для непригодного провайдера проверяется отсутствие сессии и потока.

### Стоимость фонового режима

При выборе провайдера учитывается стоимость опроса. Медленные датчики имеют
свой срок актуальности и обновляются с подходящей им частотой, даже если
оверлей обновляется чаще. ETW обрабатывает поток событий и передаёт
ограниченные агрегаты за интервал. Кеши и очереди в RAM имеют пределы,
а временные состояния и дескрипторы освобождаются при остановке.

Для нового провайдера нужны сравнимые замеры в Release на одном ПК. Сравниваются
CPU, рабочий набор памяти, число потоков и дескрипторов, а также медиана и p95
длительности цикла. Основной режим сравнения — оверлей активен, клиент закрыт
в трей. Цель 50 МиБ относится к этому режиму. Открытую статистику измеряют
отдельно. Поддерживаемый провайдер сравнивается под нагрузкой, неподдерживаемый
— по отсутствию постоянного фонового расхода.

### Порядок применения к новым подсистемам

1. Описать контракт нового показателя или найти существующий контракт того же
   показателя. Определить границы между моделью, сборщиком и потребителями.
2. Проверить, как новый провайдер определяет применимость, освобождает
   ресурсы и восстанавливается после сбоя. Сравнить нагрузку до и после.
3. Подключать подсистемы по одной. Общий интерфейс выделяется
   там, где его могут использовать несколько реальных источников с одинаковым
   контрактом. Изменения оцениваются по измерениям и прохождению тестов.

## Текущее устройство проекта

### Границы компонентов

Обязательное решение: [ADR-0001 — независимый updater](decisions/0001-independent-updater.md).
Обновление и основной монитор — отдельные процессы. В checkout нативный
Git-launcher проверяет upstream до запуска монитора, поэтому ошибка монитора
не мешает получить исправление на следующем запуске. Установленный launcher
проверяет GitHub Releases при открытии клиента, а не при обычном запуске.
Скачиваемый FluxTop.exe использует
WinHTTP, проверяет SHA-256/размер/тег и извлекает встроенный монитор. В checkout
нативный `FluxTopSource.exe` отдельно выполняет Git fetch, CMake/CTest и запуск
монитора; исходный автозапуск выполняет `FluxTopSourceAutostart.exe`. Для
установленного EXE используется собственный launcher без Git и компилятора.
Деинсталлятор `Uninstall-FluxTop.exe` встроен в скачиваемый EXE и извлекается
при установке; он удаляет только программные компоненты, сохраняя данные.
Подробнее: [PUBLISHING.md](PUBLISHING.md).

```text
Windows API -> ProcessCollector ----+
PDH --------> GpuCollector ---------+-> Snapshot -> сортировка -> console / JSONL
ETW --------> NetworkCollector ----+           -> Overlay / client
                                   |           -> HistoryWriter (SQLite)
Foreground events -> SceneManager (планируется)
```

Консольный режим выполняет сбор и вывод в одном потоке. Режим оверлея
использует отдельный поток сбора и Win32 message loop на UI-потоке.
Один общий Sampler формирует метрики в обоих режимах; UI получает последний
снимок через ограниченный mailbox и PostMessage. Клиент настроек создаётся по
запросу и уничтожается при закрытии. При скрытых обоих окнах сбор и история
продолжаются. Иконки извлекаются и сжимаются отдельным потоком
с ограниченной очередью и SQLite-кешем. Постоянного busy loop и render loop нет.
Модель снимка отделена от Windows API; детали UI — в [описании оверлея](OVERLAY.md).
Для UI единицы CPU/RAM/сети и отсутствие показаний задаются в одном
`metric_text.hpp`; код оверлея и статистики лишь выбирает значения для показа.
`overlay_ini.hpp` изолирует чтение/запись общих настроек в секции `[overlay]`,
а `windows.hpp` — преобразование UTF-8 для отображения и регистрацию
Win32-классов. Строгая проверка UTF-8 в Git-launcher намеренно независима:
некорректный вывод Git не должен маскироваться заменой символов.

### Данные

v52: [ETW-время приложений по логическим CPU](CPU_ETW.md) использует ту же kernel-
сессию, что физическая дисковая атрибуция, с отдельным raw-QPC потребителем.
Новые поля не изменяют общий CPU, PDH v51 и AutoScore. Качество, интервалы и
группировка описаны в отдельном документе.

Снимок содержит UTC-время, количество процессов, длительность сбора,
число недоступных процессов, собственные ресурсы и список метрик.
Строка процесса содержит PID, время создания, имя и optional-показатели.
CPU рассчитывается из разности kernel + user time и монотонного времени
между измерениями, делённой на число активных логических процессоров.
Baseline хранится только для процессов текущего снимка: завершённые
процессы удаляются, повторно использованный PID получает новый baseline.

GPU-экземпляры PDH связываются по PID. Связывание не атомарно со снимком
процессов, поэтому возможна погрешность при очень короткоживущих процессах
и повторном использовании PID. Слияние для нового baseline пропускается.
Неуспешный опрос не должен оставлять прошлые значения как актуальные.
GPU RAM процесса запрашивается через D3DKMTQueryVideoMemoryInfo с проверкой
creation time; память всей системы — GPU Adapter Memory, а не сумма процессов.
GetSystemTimes и GlobalMemoryStatusEx дают системные CPU/RAM.
NetworkCollector владеет отдельной ETW-сессией TCP/UDP, потребитель работает
в отдельном потоке, в RAM только агрегаты последнего интервала по PID.
Снимок содержит системные Rx/Tx и скорости каждого процесса. Сеть можно
отключить --no-network; подробности и границы в [OVERLAY.md](OVERLAY.md).

Сцены впоследствии идентифицируют приложение по нормализованному пути EXE,
с дополнительными правилами окна. PID в постоянных настройках не хранится.

### Жизненный цикл ресурсов

- HANDLE и PDH query закрываются через RAII, включая пути исключений.
- Первый CPU/GPU sample может быть неизвестен, пока нет двух измерений.
- GPU не инициализируется при отключении сборщика.
- Динамические PDH-буферы переиспользуются и имеют защитный предел размера.
- У UI нет перерисовки 60 FPS; обновление приходит после снимка или изменения настроек.
- При скрытии оверлея render target освобождается.
- При закрытии настроек уничтожается окно и принадлежащие ему ресурсы.
- История накапливается в ограниченных агрегатах и записывается фоновым
  потоком после завершения интервала; UI-поток не выполняет SQLite-запись.
- История агрегируется по завершённым минутам/часам/суткам, хранит суточные
  агрегаты до 3660 дней и останавливает запись при угрозе лимиту 50 ГиБ.
  Рабочие очереди и кеши в RAM ограничены; см. [HISTORY.md](HISTORY.md).
- Бюджет 50 МиБ применяется к активному оверлею с клиентом в трее.
  Открытый клиент/аналитика имеют отдельные показатели; после закрытия их
  ресурсы освобождаются. См. [политику истории](HISTORY.md).

### Ошибки и безопасность

Отказ доступа к отдельному процессу — нормальное частичное измерение.
Ошибка создания системного snapshot — ошибка всего цикла и ненулевой код выхода.
Отказ GPU backend не останавливает CPU/RAM; экспорт отражает недоступность.
Launcher запрашивает UAC для монитора после подготовки версии; Git и сборке
повышение не требуется. Для автоматизации есть `-StandardUser`.
Границы прав описаны в [ADR-0002](decisions/0002-administrator-monitor.md).
Сам сборщик не делает сетевых запросов. Загрузка драйверов и изменение параметров
наблюдаемых процессов не предусмотрены. Пользовательский автозапуск реализован
через ярлык Windows, задержку 30 секунд и стандартный запрос UAC. Для
установленного выпуска автозапуск использует его Win32 launcher, для checkout —
оконный нативный `FluxTopSourceAutostart.exe`. Исходный launcher перед стартом
проверяет Git upstream и выполняет сборку/CTest; загруженный EXE проверяет
GitHub Releases только при открытии клиента. Жизненный цикл описан в
[документации обновлений](UPDATING.md).
Целевой протокол включает подтверждение готовности монитора и ограниченный
fallback при провале старта. В текущем launcher-е пока проверены сборка и CTest;
подтверждение `ready` и восстановление после раннего падения ещё не реализованы.

Экспорт — UTF-8 JSON Lines, одна запись на снимок, `null` для неизвестного.
stdout содержит только данные выбранного формата, диагностика — stderr.
Строки имён экранируются. Полные пути и window titles не входят в начальный экспорт.
