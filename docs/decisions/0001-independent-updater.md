# ADR-0001: обновление независимо от запуска приложения

**Статус:** принято как обязательное архитектурное решение.

## Причина

Выпущенная версия монитора может завершаться до появления интерфейса,
не загружаться из-за повреждённого EXE или падать при чтении своих настроек.
Такой сбой не должен лишать пользователя автоматического получения исправления
при следующем запуске FluxTop.

## Решение

Обновление и мониторинг выполняются разными процессами:

- **Updater/launcher** — самостоятельная точка входа. Проверяет Git, готовит
  версию, выбирает EXE, запускает его и проверяет готовность старта.
- **Monitor (`fluxtop.exe`)** — сбор данных, оверлей, трей, настройки и история.
  Его успешный запуск не является условием работы updater-а.

Ярлыки, обычный запуск и будущая автозагрузка указывают на updater/launcher.
Прямой запуск EXE остаётся техническим режимом без автоматического восстановления.

```text
Запуск пользователем / вход в Windows
                  |
         самостоятельный updater
                  |
       проверка Git и получение фикса
                  |
      подготовка и проверка кандидата
                  |
       запуск отдельного monitor.exe
                  |
       подтверждение готовности старта
                  |
       updater завершает свою работу
```

## Обязательные свойства

1. Проверка обновлений предшествует попытке запуска монитора, даже если
   установленный EXE отсутствует, повреждён или ранее аварийно завершился.
2. Updater не загружает DLL монитора и не требует открытия его GUI,
   базы истории, профилей или успешной инициализации сборщиков.
3. Адрес upstream, минимальные настройки обновления и состояние версий хранятся
   независимо от пользовательской базы монитора. Ошибка её чтения не отключает
   проверку обновлений. Явное пользовательское отключение обновлений сохраняется.
4. Ошибка монитора не удаляет и не отключает updater, его ярлык или запись
   автозагрузки. При следующем старте проверка Git выполняется снова.
5. Кандидат готовится отдельно от установленных EXE. Сохраняются fast-forward,
   запрет перезаписи локальных правок и проверки сборки/тестов.
6. Updater имеет собственные минимальные зависимости. Его обновление должно
   проверяться отдельно; исправность самого updater-а не доказывается тестами монитора.

## Подтверждение старта и восстановление

Успешная сборка и создание процесса ещё не означают успешный запуск приложения.
Целевая схема различает **подготовленную**, **ожидающую подтверждения**,
**работоспособную** и **неудачно запущенную** версии.

После запуска monitor передаёт updater-у сигнал `ready` через локальный IPC
с уникальным идентификатором попытки. Сигнал отправляется после инициализации
обязательного ядра и готовности обслуживать цикл приложения. Необязательный
недоступный GPU-сборщик сам по себе не считается провалом старта.
Предварительный timeout подтверждения — 15 секунд, уточняется замерами.

Только после `ready` кандидат становится последней подтверждённо рабочей версией.
Updater затем завершается и не остаётся постоянным фоновым процессом.
Запрос UAC для монитора относится к этапу запуска и не является условием
проверки обновлений; см. [ADR-0002](0002-administrator-monitor.md).
Это проверка старта, а не обещание отсутствия последующих ошибок во время работы.

Если процесс не создан, завершился до `ready` или не подтвердил старт:

- Записать причину и идентификатор версии в отдельный локальный журнал updater-а.
- Сохранить предыдущую подтверждённую версию; допускается одна попытка её запуска.
- Не запускать бесконечный цикл перезапусков и не оставлять два монитора.
  Перед fallback убедиться, что неудачный кандидат завершился; принудительное
  завершение допускается только для процесса, созданного этой попыткой updater-а.
- При следующем обычном запуске снова проверить upstream. Новый commit с фиксом
  должен устанавливаться без необходимости открыть неисправное приложение.

Без сети или при отсутствии нового исправления восстановление использует
сохранённую рабочую версию. Если её нет, updater завершает попытку с понятной
диагностикой; сам факт сбоя не запрещает проверку при следующем старте.

## Соответствие текущего прототипа

Уже реализовано: PowerShell launcher выполняется отдельно от C++-сборщика,
проверяет Git перед `Start-Process`, собирает кандидата и сохраняет предыдущий EXE.
Для проверки обновлений ему не требуется успешный запуск старого монитора.

Ещё требуется: IPC `ready`, ограниченное ожидание старта, обработка падения
после создания процесса и выбор предыдущей версии по подтверждённому старту.
Текущий `last-good.json` означает успешную сборку и CTest, а не подтверждённый
пользовательский запуск. Сейчас launcher завершается сразу после создания процесса.

## Приёмочные сценарии

1. Установленный монитор падает до `main`: следующий запуск точки входа получает
   исправление из локального тестового Git remote и запускает исправленную версию.
2. Текущий EXE отсутствует или повреждён: updater продолжает проверку и установку.
3. Настройки или база монитора повреждены: механизм обновления остаётся доступным.
4. Кандидат успешно собран, но падает до `ready`: рабочая версия не теряется,
   fallback выполняется не более одного раза.
5. Кандидат завис до `ready`: timeout не порождает второй работающий монитор.
6. После неудачного кандидата опубликован новый commit: следующая попытка
   устанавливает его автоматически, без запуска неисправной версии для обновления.
7. Офлайн-старт, локальные изменения и явное отключение обновлений сохраняют
   документированное поведение; автозапуск использует тот же независимый путь.
