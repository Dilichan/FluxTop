# Участие в разработке

FluxTop разрабатывается открыто. Изменения должны сохранять нативную
архитектуру и учитывать стоимость фоновой работы.

Перед изменением прочитайте [стек](docs/STACK.md) и [архитектуру](docs/ARCHITECTURE.md).
Для заметного изменения архитектуры сначала опишите причину, альтернативы
и ожидаемое влияние на CPU, память и совместимость в issue или PR.

## Код и проверки

Нужны Windows 10/11 x64, Visual Studio Build Tools с C++20 и Windows SDK,
CMake 3.24+. В x64 Developer PowerShell:

```powershell
cmake --preset windows -DFLUXTOP_RELEASE_TAG:STRING=v0.2.6
cmake --build --preset release
ctest --preset release
# source_git_update, source_process_contract, source_launcher_fallback
# и source_bootstrap_policy теперь входят в CTest
```

CMake кеширует `FLUXTOP_RELEASE_TAG`; при повторной сборке в старом каталоге
явно задавайте новый тег, чтобы не оставить метаданные предыдущего релиза.
Тесты `source_git_update`, `source_launcher_fallback`, `native_uninstall_fixture`
и `installation_fixture` входят в CTest; сетевой ETW-тест может быть `Skipped`
без административных прав. Python и PowerShell не требуются для упаковки EXE.

Без Visual Studio generator можно использовать Ninja:

```powershell
cmake -S . -B build/ninja -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/ninja
ctest --test-dir build/ninja --output-on-failure
```

Сборщик/CLI: build/Release/fluxtop.exe (у Ninja — build/ninja/fluxtop.exe).
Исходный Git-launcher: build/Release/FluxTopSource.exe; автозапуск:
build/Release/FluxTopSourceAutostart.exe. Скачиваемый launcher:
build/package/Release/FluxTop.exe. Смотрите
[публикацию релизов](docs/PUBLISHING.md), прежде чем ставить тег.
Для диагностики: fluxtop.exe --help, --jsonl, --samples N, --no-network.
FLUXTOP_DATA_DB / FLUXTOP_LOG_PATH / FLUXTOP_OVERLAY_SETTINGS задают
изолированные файлы данных, журнала и настроек для тестов. Network-test пропускается без административного
токена; отдельно проверьте его под администратором. Автоматизация не подтверждает UAC.

- C++20, Unicode Win32 API, RAII для системных ресурсов.
- Избегайте неограниченных кешей, очередей, частого polling и постоянных UI-анимаций.
- Проверяйте расчёты CPU, смену идентичности процесса и отсутствующие данные тестами.
- Ошибки доступа не превращайте в нули или выдуманные показатели.
- PR должен включать описание поведения, способ проверки и ограничения.
- Для оптимизаций приложите сравнимые замеры Release до и после.
- При локализованной MSVC/Ninja проверяйте отслеживание заголовков. Если `/showIncludes`
  неправильно распознаётся из-за кодировки, после изменения заголовков выполняйте
  `cmake --build build/ninja --clean-first`, чтобы не смешать несовместимые объекты.
- Не добавляйте бинарники, логи, EXE-пути своей машины, базы истории и секреты.

## Обязательные тесты и защита от регрессий

**Каждое изменение поведения включает тесты.** Для новой функции нужны
позитивный, граничный и негативный сценарии. Для исправления бага сначала
создаётся воспроизводящий тест, который падает до исправления и проходит
после него. Если автоматизировать аппаратный/UI-сценарий нельзя, в PR
обязательны шаги ручной проверки, среда и явно непроверенные условия.

**Старые функции не должны переставать работать после нового патча.** Автор
фиксирует затронутые входы, выходы и контракты соседних подсистем и добавляет
регрессионные проверки на их взаимодействие. Обязательные связки при
соответствующих изменениях: коллектор → Snapshot → группирование → AutoScore →
сортировка → оверлей/статистика → SQLite/JSONL, а для графиков — шкала,
пауза, всплывающая подсказка и отдельное окно. Нельзя проверять только наличие
функции/обработчика в исходнике: проверяйте **результат** на конкретных данных.

Минимальная матрица при изменении метрик: подтверждённый ноль, неизвестное
значение, частичное покрытие, нехватка прав, потеря событий, завершение
процесса, повторное использование PID, несколько одинаковых имён и
несколько процессов одного приложения. История, GUI и JSONL должны одинаково
трактовать доступность данных; существующие записи SQLite сохраняются.

Перед работой фиксировать commit и базовый Release CTest. После работы:
пересобрать Release, выполнить **полный** CTest и целевые тесты, а для ETW,
температур и UI — соответствующую интеграционную или ручную проверку.
`Skipped` не равен `Passed` и должен объясняться; при падении тестов патч
не готов к коммиту. Для периодически падающего JSONL нужны повторные прогоны
и диагностический вывод с кодом завершения, а не увеличение тайм-аута вслепую.

- Не ослаблять утверждения, не удалять и не пропускать старые тесты ради успеха.
- Не изменять действующий контракт без теста совместимости и обоснования.
- Новые тесты регистрировать в CMake/CTest и запускать в Windows CI.
- Фиксировать точные результаты `passed / failed / skipped`; не считать
  успешно завершённой сборку, если CTest вернул ненулевой код.
- Изменения измерительных алгоритмов дополнительно проверять на расход
  памяти/CPU, отсутствие утечек и стабильность при перезапуске.

Текущая последовательность и критерии готовности этапов — в
[дорожной карте](docs/ROADMAP.md).
## Правила ведения документации

Сохраняем небольшой набор **постоянных** документов: README, требования,
архитектуру и ADR, стек, дорожную карту, спецификации основных компонентов,
методику измерений, руководство пользователя, публикацию, безопасность и
правила разработки. История выпусков (`docs/RELEASE_NOTES.md`) обязательна:
её читает автоматическая публикация GitHub Releases.

**Не создавать в репозитории отдельные Markdown-файлы под каждый патч, багфикс,
замер, номер скрипта или промежуточный эксперимент.** Описание изменения
вносится в соответствующий существующий фундаментальный документ; заметки
для публичного релиза — в `docs/RELEASE_NOTES.md`. Временные отчёты, логи,
применяющие скрипты и результаты тестов остаются вне отслеживаемого дерева Git.
Новый документ допускается только при появлении нового устойчивого интерфейса,
подсистемы или архитектурного решения, которые нельзя разумно описать в
существующей спецификации.

## Сторонний код

Новый код проекта распространяется по MIT. При заимствовании сначала
проверьте совместимость лицензии, сохраните атрибуцию и добавьте notice.
Простая ссылка на другой репозиторий не даёт разрешения копировать его код.
Новые зависимости требуют зафиксированной версии и описания происхождения.

Сообщение об ошибке должно содержать версию/commit, Windows, оборудование,
настройки запуска и минимальные шаги воспроизведения. Перед публикацией
логов удалите персональные сведения и имена внутренних приложений.

## Обязательные поведенческие и регрессионные тесты (v37)

Изменение считается завершённым только после успешной Release-сборки,
полного CTest и проверки затронутых пользовательских сценариев. Проверки
наличия строк в коде (`*_policy`) дополняют, но **не заменяют** тесты реальных
вычислений и наблюдаемого поведения.

- **Новая функция:** добавить unit-тест нормального результата, граничных
  значений и недоступного источника; добавить интеграционный тест, если данные
  переходят границу подсистем или попадают в JSONL, SQLite либо UI.
- **Исправление ошибки:** сначала создать тест, воспроизводящий прежнюю ошибку,
  затем исправить код и убедиться, что тест проходит. Сохранять тест навсегда.
- **Изменение существующей функции:** повторно проверить прежний контракт,
  включая нулевые значения, `nullopt`, ошибки доступа, PID reuse и отмену задач.
- **Изменение формата данных:** проверить чтение старых данных, неизменность
  прежних полей и корректную обработку неизвестных значений.
- **Изменение UI:** проверить встроенное окно, отдельное окно, оверлей,
  сохранение настроек и отсутствие побочных эффектов для остальных страниц.

Матрица смежных контрактов (проверять затронутую часть цепочки в обе стороны):

| Источник/этап | Проверка на входе | Проверка на выходе и у потребителя |
| --- | --- | --- |
| CPU/GPU/ETW/температуры | PID+время создания, права, валидность, статус | `Snapshot`: известный ноль не равен неизвестному |
| Агрегация приложений | общая EXE-идентичность либо доказанная родословная | нет смешивания разных процессов, корректная GPU RAM |
| AutoScore | только измеренные и разрешённые пользователем метрики | сортировка, всплески, цвета не меняются от скрытых данных |
| Оверлей/клиент | группированные данные и состояние настроек | таблицы, подсказки, графики и отдельные окна |
| SQLite/история | наблюдения и стабильная идентичность | аптайм не удваивается, нет вымышленных нулевых баллов |
| Статистика | SQLite и живые измерения | корректные периоды, шкалы и выбор приложения |
| JSONL | `Snapshot` и контракт версии схемы | `null` вместо неизвестных значений, прежние ключи сохранены |

`regression_contracts` объединяет несколько границ подсистем; тесты
`core`, `history`, `statistics`, `disk_attribution`, `temperature_detection` и
`jsonl_contract` проверяют специализированные инварианты. Одна только
успешность `*_policy` недостаточна. Все обязательные тесты должны пройти
до коммита и в Windows CI. `network` может быть `Skipped` без повышения прав;
остальные пропуски требуют выяснения причины.

Проверка перед коммитом: `pwsh -NoProfile -File tools/Check-Regression.ps1`.
Полный прогон выполняется от администратора. Постоянные испытания v54,
повторы нестабильных сценариев и отключённые интерактивные проверки описаны
в [матрице стабильности](docs/STABILITY.md). Пропуск обязательного
административного теста не является успешной проверкой.
Патч v37 настраивает локальный `pre-commit` hook через `core.hooksPath`;
он блокирует коммит при ошибке сборки или тестов. Локальный hook можно обойти,
поэтому окончательный запрет слияния требует обязательного CI-check в
настройках защиты ветки GitHub. Нельзя считать неудачный тест успешным из-за
последующей команды `Write-Host`.
