# Участие в разработке

FluxTop разрабатывается открыто. Изменения должны сохранять нативную
архитектуру и учитывать стоимость фоновой работы.

Перед изменением прочитайте [стек](docs/STACK.md) и [архитектуру](docs/ARCHITECTURE.md).
Для заметного изменения архитектуры сначала опишите причину, альтернативы
и ожидаемое влияние на CPU, память и совместимость в issue или PR.

## Код и проверки

Нужны Windows 10/11 x64, Visual Studio Build Tools с C++20 и Windows SDK,
CMake 3.24+. В x64 Developer PowerShell:

```powershell
cmake --preset windows
cmake --build --preset release
ctest --preset release
powershell.exe -NoProfile -File tests/update_tests.ps1
powershell.exe -NoProfile -File tests/launcher_tests.ps1
powershell.exe -NoProfile -File tests/elevation_tests.ps1
```

Без Visual Studio generator можно использовать Ninja:

```powershell
cmake -S . -B build/ninja -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/ninja
ctest --test-dir build/ninja --output-on-failure
```

Сборщик/CLI: build/Release/fluxtop.exe (у Ninja — build/ninja/fluxtop.exe).
Скачиваемый launcher: build/package/Release/FluxTop.exe. Смотрите
[публикацию релизов](docs/PUBLISHING.md), прежде чем ставить тег.
Для диагностики: fluxtop.exe --help, --jsonl, --samples N, --no-network.
FLUXTOP_DATA_DB / FLUXTOP_LOG_PATH / FLUXTOP_OVERLAY_SETTINGS задают
изолированные файлы данных, журнала и настроек для тестов. Network-test пропускается без административного
токена; отдельно проверьте его под администратором. Автоматизация не подтверждает UAC.

- C++20, Unicode Win32 API, RAII для системных ресурсов.
- Избегайте неограниченных кешей, очередей, частого polling и постоянных UI-анимаций.
- Проверяйте расчёты CPU, смену идентичности процесса и отсутствующие данные тестами.
- Ошибки доступа не превращайте в нули или выдуманные показатели.
- PR должен включать описание поведения, способ проверки и ограничения.
- Для оптимизаций приложите сравнимые замеры Release до и после.
- При локализованной MSVC/Ninja проверяйте отслеживание заголовков. Если `/showIncludes`
  неправильно распознаётся из-за кодировки, после изменения заголовков выполняйте
  `cmake --build build/ninja --clean-first`, чтобы не смешать несовместимые объекты.
- Не добавляйте бинарники, логи, EXE-пути своей машины, базы истории и секреты.

## Правила ведения документации

Сохраняем небольшой набор **постоянных** документов: README, требования,
архитектуру и ADR, стек, дорожную карту, спецификации основных компонентов,
методику измерений, руководство пользователя, публикацию, безопасность и
правила разработки. История выпусков (`docs/RELEASE_NOTES.md`) обязательна:
её читает автоматическая публикация GitHub Releases.

**Не создавать в репозитории отдельные Markdown-файлы под каждый патч, багфикс,
замер, номер скрипта или промежуточный эксперимент.** Описание изменения
вносится в соответствующий существующий фундаментальный документ; заметки
для публичного релиза — в `docs/RELEASE_NOTES.md`. Временные отчёты, логи,
применяющие скрипты и результаты тестов остаются вне отслеживаемого дерева Git.
Новый документ допускается только при появлении нового устойчивого интерфейса,
подсистемы или архитектурного решения, которые нельзя разумно описать в
существующей спецификации.

## Сторонний код

Новый код проекта распространяется по MIT. При заимствовании сначала
проверьте совместимость лицензии, сохраните атрибуцию и добавьте notice.
Простая ссылка на другой репозиторий не даёт разрешения копировать его код.
Новые зависимости требуют зафиксированной версии и описания происхождения.

Сообщение об ошибке должно содержать версию/commit, Windows, оборудование,
настройки запуска и минимальные шаги воспроизведения. Перед публикацией
логов удалите персональные сведения и имена внутренних приложений.
